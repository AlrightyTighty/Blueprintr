## The idea in one sentence
Guidr is a narrated, interruptible, walkable tour of a repo's application code and Terraform infrastructure: it links the two into one graph, turns real request paths into guided journeys, and lets you rehearse an outage or a change before it happens.

Tagline: "A guided tour of your cloud, including the outage before it happens."

## Positioning and competition (read before pitching)

## Core product

### Journeys and stops
- A **journey** is a real path through the graph from an entry point (domain, API route, queue, schedule) to where the data ends up. Example: "A customer places an order" goes domain, CloudFront, API Gateway, Lambda, DynamoDB, SQS, email Lambda. Generated by traversing the linked graph.
- A **stop** is one node on a journey. The camera glides to it, the guide speaks, and the screen shows the real code lines beside the Terraform block that runs them. The guide covers what it is, why it exists, and what it touches.
- **Warnings are stops too.** Findings from the graph appear on the tour: "Watch your step, this role allows every S3 action but the code only reads one bucket."
- Every tour starts at the domain, the front door.

### Tour types
1. **First day:** the main journeys through the system.
2. **Follow a request:** one chosen journey end to end.
3. **Disaster tour:** pick or kill a resource (or load a plan that replaces it). The failure cascades along the graph as an animation, and the guide stays unnervingly calm while narrating user-visible symptoms.
4. **Change tour:** paste `terraform show -json plan.out`. Replace and destroy resources turn red, everything downstream turns amber, including the exact code that depends on them, then the guide walks through what the change touches and a safer order of operations.

### Interaction
- **Interrupt anytime.** Ask "why does this function need that role?" and the guide answers from graph queries, then resumes the tour.
- **Guide personalities** (ElevenLabs voices): at least two, for example a calm museum docent and an overexcited one, switchable in the UI.
- **Shareable:** export a tour as a link or an audio file (stretch).

### Findings (nearly free from the graph, surfaced as warning stops)
- Permission gaps: code calls an action the role does not allow (e.g. dynamodb:DeleteItem).
- Over-broad IAM: role allows s3:* but code only reads one bucket.
- Unmanaged resources: a bucket name hardcoded in code that is not in Terraform (drift).

### Domains as a node type
Route 53 records and CDN aliases are graph nodes, so every tour begins at the domain and the demo can end on "this site's domain traces to its CDN, which traces to its bucket."

## How code gets linked to resources (every edge carries a confidence label shown in the UI)
| # | Method | Example | Confidence |
|---|---|---|---|
| 1 | Declared references in IaC | aws_lambda_function.api references aws_iam_role.api_role and aws_dynamodb_table.orders | Certain |
| 2 | Env var join | Terraform sets TABLE_NAME = aws_dynamodb_table.orders.name on a Lambda; code reads process.env.TABLE_NAME | High |
| 3 | Code-to-compute mapping | Lambda handler/source_dir, Dockerfile build context, compose build: path maps a code folder to the resource that runs it | High |
| 4 | Gemini inference | SDK call like s3.putObject with a config-built bucket name; Gemini reads context and picks the likely resource | Labeled "inferred" |

The env var is the bridge between the IaC world and the code world. Inferred hops are labeled as inferred in the UI and in the narration. Being upfront about this is a credibility point.

## How each target track does a real job
**Gemini**
- Writes each tour script from the graph as structured output, with file and line citations per stop
- Rule: the guide only talks about nodes that exist in the graph; every claim cites a file and line
- Answers interruptions by calling graph query functions instead of guessing ("what touches the users table?")
- Structured-output extraction to resolve resources static parsing cannot (method 4)
- Translates failure cascades into user-visible symptoms ("checkout returns 500 errors, order emails stop, the admin dashboard loads but shows no orders")
- Suggests safer change sequences (create_before_destroy, dual-write and backfill, staged migration)

**ElevenLabs**
- The voice is the product, not an add-on: the guide narrates every stop in sync with the camera
- Selectable personalities (calm docent, overexcited guide), each a distinct voice
- Voice interruptions and Q&A via an ElevenLabs conversational agent wired to the graph query tool
- Disaster tour tone: gentle tour guide narrating a cascading failure (the contrast is a deliberate laugh)

**GoDaddy**
- Registration prize, so the work is the name and domain fit. Name is Guidr; check guidr.* availability on the TLDs the track offers and register early. Fallbacks: another TLD, or a prefix like useguidr / tryguidr. Availability is NOT yet verified.
- Domains-as-graph-nodes ties the domain into the product story: every tour starts at the front door.

## Scope (keep it narrow and working)
- Terraform + AWS only, a small set of resource types: Lambda, S3, DynamoDB, SQS, IAM roles/policies, API Gateway, Route 53/CloudFront
- App code: Python and JavaScript/TypeScript only
- Static analysis only. Never run terraform apply or any repo code. Reading plan JSON is safe; say so on stage.
- Build a demo repo we control with planted traps: an unmanaged hardcoded bucket, an over-permissive role, a function missing a permission it needs. Hand-verify every journey in it.
- Modules, count and for_each are out of scope (say "future work"). Simple var/local references resolved from defaults in variables.tf; the rest shown as labeled unresolved nodes.

## Tech stack (decided)
- **React SPA**: Vite + React + TypeScript, Tailwind, React Flow (graph and camera), Zustand (state), React Router only if needed
- **Thin serverless proxy** (Vercel/Netlify /api functions) because API keys can't live in the browser. Jobs: call Gemini, call ElevenLabs (return audio, or give a signed URL for the conversational agent), keep keys secret. Alternative: small Express/FastAPI service if the backend teammate prefers Python.
- **HCL parsing:** use a library, don't write a parser. Recommended: @cdktf/hcl2json (HashiCorp's Go HCL parser compiled to WASM; call parse("main.tf", contents) and get JSON). Verify current maintenance status before depending on it. Python fallback: python-hcl2.
  - Preferred: run it in the proxy (Node) for reliability. In-browser WASM loading through Vite is the likeliest source of trouble, so test it in the first hour; if it fights us, parse in the serverless function (then adjust the pitch's privacy line, since repo contents pass through the proxy).
  - The plan overlay needs no HCL parser: terraform show -json is already structured JSON.
- Fetch repo files in the browser via GitHub REST API (public repos allow CORS) or a pasted/dropped folder.
- Code scanning (env var reads, SDK calls) with regex plus a lightweight parser (Babel or tree-sitter WASM).
- Graph building, journey extraction and cascade propagation: pure TypeScript modules in the browser.
- Deploy on whatever is fastest (Vercel).

## Graph and tour types (starting contract between frontend and backend)
```ts
export type NodeKind =
  | "domain" | "cdn" | "api_gateway" | "lambda" | "s3" | "dynamodb"
  | "sqs" | "iam_role" | "code_file" | "unresolved";

export type Confidence = "certain" | "high" | "inferred";

export interface GraphNode {
  id: string;
  kind: NodeKind;
  label: string;
  source?: { file: string; line?: number };
}

export interface GraphEdge {
  id: string;
  from: string;
  to: string;
  relation: "references" | "reads" | "writes" | "invokes" | "grants" | "runs" | "routes";
  confidence: Confidence;
  evidence?: string;
}

export interface CodeRef {
  file: string;
  startLine: number;
  endLine: number;
}

export interface Stop {
  nodeId: string;
  script: string;
  codeRefs: CodeRef[];
  warnings: string[];
  inferred: boolean;
}

export interface Journey {
  id: string;
  title: string;
  kind: "first_day" | "request" | "disaster" | "change";
  stops: Stop[];
}
```

## The parts we still have to write (the actual core of the project)
1. **Reference extraction and env var bridge.** The HCL parser returns structure, not relationships. References come back as interpolation strings like "${aws_dynamodb_table.orders.name}", so the linker must walk every attribute value in each resource block, regex-extract references (aws_type.name.attribute) to create declared edges, and find env var blocks (e.g. a Lambda's environment.variables) to record which resource each variable points to. About 50-100 lines of TypeScript.
2. **Journey extraction.** Find entry points (domains, API routes, queues, schedules), traverse the graph to sinks, and turn each path into an ordered list of stops. Label any hop with inferred confidence.
3. **Cascade propagation.** Given a killed or replaced node, walk dependents in order. This drives both the disaster animation and the change tour.

## Build order (steps 1-6 = a complete demo)
1. Parse Terraform into resource nodes with declared edges
2. Scan app code and link by env var and handler path
3. Graph UI with click-to-select and the camera moving along a path

## Demo plan (~3 minutes)
1. Load the demo repo; the graph assembles with the domain at the front, code nodes, and resource nodes, edges styled by confidence.
2. Start "Follow an order"; the guide narrates stop by stop as the camera moves, showing code and Terraform side by side.
3. Interrupt mid-tour with a question and get a grounded answer, then the tour resumes.
4. Switch to the disaster tour on the orders table; the cascade runs while the guide stays calm; symptoms are narrated.
5. Show a warning stop (permission gap or unmanaged bucket) and, if time allows, load a plan for the change tour.
6. End back at the domain.
Cache demo-repo results and keep a backup recording in case of Wi-Fi or API failure.

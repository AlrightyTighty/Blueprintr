## The idea in one sentence
Ripplemap is a narrated, interruptible, walkable tour of a repo's application code and infrastructure code (Terraform, CloudFormation or CDK output): it links the two into one graph, turns real request paths into guided journeys, and lets you rehearse an outage or a change before it happens.

Tagline: "A guided tour of your cloud, including the outage before it happens."

## Core product

### Journeys and stops
- A **journey** is a real path through the graph from an entry point (domain, API gateway, function) to where the data ends up. Example: domain, CloudFront, API Gateway, Lambda, DynamoDB, SQS, worker Lambda. Generated by traversing the linked graph, in the browser (`frontend/src/core/journeys/`).
- A **stop** is one node on a journey. The camera glides to it, the guide speaks, and the screen shows the real code lines beside the infrastructure block that runs them. The guide covers what it is and what it touches. The demo project (`/demo`) shows real code; for other projects the code panel shows file and line and links out to GitHub, because the backend never stores source.
- **Warnings are stops too.** Findings from the graph appear on the tour: "Watch your step: this role allows every S3 action but the code only uses one bucket."
- Every tour starts at the domain, the front door, when the graph has one.

### Tour types (all built)
1. **First day:** the main journeys through the system.
2. **Follow a request:** one chosen journey end to end.
3. **Disaster tour:** pick a resource and "pull the plug." The guide walks the cascade of everything that depends on it, stop by stop with the camera, narrating symptoms in a deliberately calm tone. (There is no separate animation of the cascade; it is told stop by stop.)
4. **Change tour:** paste `terraform show -json plan.out`. Replaced and destroyed resources are red, everything downstream is amber, including the exact code that depends on them, then the guide walks through what the change touches. Terraform plans only; CloudFormation change sets are not read.
5. **Endpoint tour ("call" an endpoint):** type a method and path such as `GET /orders/123`, or pick one of the project's endpoints. The backend finds the endpoint API Gateway would choose (HTTP API route, REST API method, or Lambda function URL) and follows the request through domain/CDN, API, route, integration, Lambda, handler, the functions it calls, and the data they touch, then on into any worker a queue triggers (marked as background work). Nothing is sent to the real API.
   - Honest limit: when several routes share one Lambda handler, the infrastructure cannot say which branch a route takes inside it, so the tour shows everything the handler can reach and says so. Routes declared inside code (Express, Fastify, Flask) are not read. That is the main thing that would make endpoint tours differ route by route.

### Interaction
- **Ask a question anytime** in the Ask panel (typed). With a real project, Gemini answers by calling graph queries (function calling over `POST /projects/{id}/graph/query`), so answers come from the graph. The demo project answers from a keyword-matching offline stand-in, and says so.
- **Voice:** one guide voice (the ElevenLabs voice set in `ELEVENLABS_VOICE_ID`). A voice control has three modes: Off (captions only), Saved (plays pre-recorded demo clips, free), Live (ElevenLabs speaks any other line on demand, costs credits).
- **Not built:** selectable guide personalities (the brief wanted a calm docent and an overexcited one), spoken questions via an ElevenLabs conversational agent (the backend has the session and tool endpoints; nothing in the UI uses them), and exporting a tour as an audio file.
- **Shareable (built):** projects can be shared with people as owner, editor or viewer, and by a read-only link; invitations and an activity log are included.

### Findings (surfaced as warning stops and in the Details tab)
- Permission gaps: code calls an action the role does not allow (e.g. dynamodb:DeleteItem).
- Over-broad IAM: role allows s3:* but code only uses one bucket.
- Unmanaged resources: a bucket name hardcoded in code that is not in the infrastructure code (drift).
- Unresolved references: unresolvable Terraform references, env vars the Lambda never sets, calls whose target could not be determined.

### Domains as a node type
Route 53 records and CDN aliases are graph nodes, so every tour begins at the domain and the demo can end on "this site's domain traces to its CDN, which traces to its bucket."

## How code gets linked to resources (every edge carries a confidence label shown in the UI)
| # | Method | Example | Confidence |
|---|---|---|---|
| 1 | Declared references in IaC | aws_lambda_function.api references aws_iam_role.api_role and aws_dynamodb_table.orders (Terraform `${...}`; CloudFormation `Ref`/`GetAtt`/`Sub`/`ImportValue` are rewritten to the same form) | Certain |
| 2 | Env var join | The Lambda's environment sets TABLE_NAME to the orders table; code reads process.env.TABLE_NAME | High |
| 3 | Code-to-compute mapping | Lambda handler and `source_dir` (or CDK `aws:asset:path` when assets are un-staged) map a code folder and handler function to the Lambda; a bare or imported call between functions becomes a `calls` edge; a resource name written literally in code is matched to the resource with that name, or flagged as unmanaged | High |
| 4 | Gemini inference | An SDK call whose target is built at runtime; Gemini picks from the candidate resources parsed from the IaC (it can only choose from that list) | Labeled "inferred" |

The env var is the bridge between the IaC world and the code world. Inferred hops are labeled as inferred in the UI and in the narration. Being upfront about this is a credibility point. Docker build contexts and compose `build:` paths are NOT mapped yet.

## How each target track does a real job
**Gemini**
- Resolves resources static parsing cannot (method 4), as structured output limited to candidates found in the parsed IaC. Built.
- Answers questions by calling graph queries instead of guessing ("what touches the users table?"). Built.
- Explains what a Terraform plan does and suggests safer alternatives (create_before_destroy, prevent_destroy, staged migration), and writes the plan's spoken briefing script. Built. Without a Gemini key these fall back to rule-based text.
- Rule: the guide only talks about nodes that exist in the graph; every claim cites a file and line.
- **Tour scripts are NOT written by Gemini.** They are generated offline and deterministically from the graph (`frontend/src/core/journeys/narration.ts`), so every sentence is grounded and cited. A Gemini-written script could replace them later; the `Stop` shape stays the same.

**ElevenLabs**
- Narrates every stop (Live mode via `POST /narrate`, cached; Saved mode plays clips generated ahead of time with `npm run narrate:demo`). Built.
- Voices the plan briefing ("This plan replaces one resource and modifies three... I'd stop here"). Built (needs ElevenLabs and audio storage configured).
- Disaster tour tone: gentle tour guide narrating a cascading failure (the contrast is a deliberate laugh).
- Not built: multiple personalities; the conversational agent wired into the UI.

**GoDaddy**
- Registration prize, so the work is the name and domain fit. Name is Ripplemap; ripplemap.wiki is registered and live (apex and www serve the site, `api.` serves the API; DNS is currently hosted at Porkbun nameservers). Whether this setup qualifies for the GoDaddy Registry track is NOT verified; check the track rules.
- Domains-as-graph-nodes ties the domain into the product story: every tour starts at the front door.

## Scope (keep it narrow and working)
- AWS only. Infrastructure code: Terraform (`.tf`), and CloudFormation templates in YAML or JSON, including `cdk synth` output (`cdk.out/*.template.json`). Resource types with names and icons: Lambda (function, event source mapping, permission, function URL), S3 (bucket, policy), DynamoDB table, SQS (queue, policy), SNS topic, IAM (role, policy, inline policy, attachment), API Gateway (HTTP API and REST API pieces), CloudFront distribution, Route 53 (zone, record). Other types still become graph nodes with a generic icon.
- App code: Python and JavaScript/TypeScript only.
- Static analysis only. Never run terraform apply, `cdk synth`, or any repo code. Reading plan JSON is safe; say so on stage. A CDK app is analysable only if its synthesized templates are in the repo.
- Public GitHub repos are linked by URL with no GitHub login; private repos need GitHub OAuth. Only the analysis is stored (never source).
- Demo repo we control with planted traps (in `backend/test/fixtures/demo`, with CloudFormation and CDK versions beside it): an unmanaged hardcoded bucket, an over-permissive role, a function missing a permission it needs. Hand-verify every journey in it; `npm run check:tours` checks them.
- Out of scope (say "future work"): Terraform modules, count and for_each, SAM (`AWS::Serverless::*`), nested stacks, Docker/compose mapping, routes declared in code. Simple var/local references resolve from defaults; the rest show as labeled unresolved nodes.

## Tech stack (as built)
- **Frontend:** Vite, React, TypeScript, Tailwind v4, React Flow (`@xyflow/react`, dagre layout), Zustand, React Router. Journey extraction, cascade propagation and tour narration run in the browser as React-free modules in `src/core/`.
- **Backend:** Fastify 5 on Node, run locally as a server and deployed as one AWS Lambda behind an API Gateway HTTP API. `pg` against Postgres (RDS in production), `zod` validation, `jose` JWTs, password hashing with scrypt. The API contract is `backend/openapi.yaml`.
- **Analysis (backend, `src/core/`):** HCL parsed with `@cdktf/hcl2json` (Go WASM, runs in Node), CloudFormation with the `yaml` package, code scanned with regex plus bracket matching (no Babel or tree-sitter). Repos are fetched server-side as GitHub tarballs and read in memory. Analysis runs in the background (a Lambda invokes itself asynchronously), so starting a run returns immediately.
- **AI:** Gemini and ElevenLabs are called from the backend (keys never reach the browser). Briefing audio is cached in S3, or on local disk when no bucket is configured.
- **Infrastructure:** AWS CDK in `iac/` (backend Lambda, API Gateway, S3 for audio; frontend S3 bucket and CloudFront). The custom domain and certificate for `api.ripplemap.wiki` were added by hand, outside CDK.
- **Database:** numbered SQL files in `database/` applied with `database/migrate.sh`; see `database/README.md`.
- **Tests:** Vitest in `backend/test/` (unit tests, an OpenAPI conformance test that fails if routes and spec drift, and an end-to-end suite that runs against a real Postgres when `TEST_DATABASE_URL` is set); `npm run check:tours` checks the tours against the demo repo.

## Repository layout
```

scripts/    snapshot:demo (bundles the real demo analysis for /demo), narrate:demo (pre-records the guide), check:tours
```
Keep `core/` free of React and HTTP so graph, journey and analysis logic can be tested without the UI or a server.

## Journey and stop types (frontend contract)
The graph and API types live in `backend/openapi.yaml` and are mirrored in `frontend/src/core/graph/types.ts`. Tours use:
```ts
export interface CodeRef { file: string; startLine: number; endLine: number }

export interface Stop {
  nodeId: string;
  script: string;
  codeRefs: CodeRef[];
  warnings: string[];
  /** True when the hop into this stop is inferred rather than proven; the guide says so. */
  inferred: boolean;
}

export interface Journey {
  id: string;
  title: string;
  kind: "first_day" | "request" | "disaster" | "change" | "endpoint";
  stops: Stop[];
}
```
An edge means "source depends on target" (a function reads a table, a Lambda assumes a role, code runs on a Lambda). Relations: references, depends_on, assumes_role, grants_access, runs_code, reads, writes, publishes, invokes, routes_to, calls.

## Demo plan (~3 minutes)
1. Open `/demo` (no account, no network needed): the graph assembles with the domain at the front, code nodes and resource nodes, edges styled by confidence.
2. Start "Follow a request" or an endpoint tour (`POST /orders`); the guide narrates stop by stop as the camera moves, with code beside the infrastructure block. Use Saved voice mode so no credits are spent.
3. Ask a question mid-tour and get a grounded answer, then resume.
4. Switch to the disaster tour on the orders table; the guide stays calm while symptoms are narrated.
5. Show a warning stop (permission gap or unmanaged bucket) and, if time allows, load a plan for the change tour.
6. End back at the domain.
A real project (linked by URL) is the stretch demo. Keep a backup recording in case of Wi-Fi or API failure.

## Risks and honesty points
- Crowded space: "explain this codebase" tools exist, and blueprintr.io and blastmap.dev overlap in places. Our edge is code linked to IaC, request journeys, and a voiced guide. Verify with a quick search (see Positioning).
- **Check marketing copy against this brief.** The landing page still says "Choose a calm docent or an overexcited guide," but there is one voice and no switcher. Either build personalities or remove that sentence before judging.
- Journey quality depends on link quality. Hand-verify the demo repo's journeys and label inferred hops. The call graph follows bare and imported calls by name, not `obj.method()`, so it is reliable for typical handler-to-helper code but not exact.
- Shared Lambda handlers make endpoint tours show everything the handler can reach (see Endpoint tour).
- Networks: on one campus network, requests to `api.ripplemap.wiki` were blocked (probably a filter on a newly registered domain) while the AWS default URL worked, and a phone hotspot fixed it. Expect this at a venue; `/demo` needs no API.
- Deployment: `cdk deploy` does not read `.env` files; backend settings come from the deploying shell. CORS allows only the origins in `CORS_ORIGIN` (comma-separated), or `FRONTEND_URL` when unset.
- Integration sprawl: always keep a working end-to-end build; never leave main broken.
- The guide must never invent: it only talks about graph nodes and cites file and line. Say plainly that humans review every conclusion.
- Never execute untrusted code; static analysis only.
